# Handoff — Persistent Multi-Model Unsloth Local-Agent MCP

Date: 2026-08-29

Status: **MULTI-MODEL UNSLOTH MCP READY — CANONICAL QWEN ROUTE**

This is the canonical current-state handoff. The numbered `1.*` handoff is
preserved only as the historical single-model baseline.

## Objective

Extend the qualified persistent Unsloth local-agent MCP with a small routing layer that:

- lists approved local-agent models;
- accepts an optional approved model alias when spawning a child;
- keeps Q4 as the default;
- rejects unknown aliases before starting a child;
- preserves the existing child authentication, provider, sandbox, workspace, and timeout behavior;
- prevents concurrent Qwen worker executions.

The installed Unsloth Python package was not patched.

## Canonical Qwen routing decision

Date: 2026-08-30

Qwen delegation now uses only:

```text
unsloth_local_agent/spawn_local_agent
```

The former native collaboration role at
`C:\Users\henry\.codex\agents\qwen38-worker.toml` was removed. It selected
`Unsloth-studio/unsloth-Qwen3.8-27B-GGUF` without selecting the Unsloth model
provider or receiving `UNSLOTH_STUDIO_AUTH_TOKEN`. Native spawning therefore
sent the model through the parent ChatGPT account route and failed before the
Unsloth endpoint received a request:

```text
The 'Unsloth-studio/unsloth-Qwen3.8-27B-GGUF' model is not supported when using Codex with a ChatGPT account.
```

The MCP is the single routing boundary because it reads the current generated
authentication from `subagent.json`, injects it only into the child process,
selects the `unsloth_api` provider, uses the approved endpoint model IDs, and
enforces the cross-process Qwen lock.

Agent instructions now require:

- Qwen, Unsloth, and local-agent requests call the MCP once with the complete task.
- Omitting `model` uses `qwen38-q4`.
- `qwen38-q5` is used only when explicitly requested or when the user asks for the higher-quality local model.
- MCP failures are returned to the user; another model is used only when the user explicitly requests a fallback.

Native `spawn_agent`, `wait_agent`, and Multi-Agent V1/V2 settings no longer
apply to the Unsloth worker. The MCP call is synchronous and owns concurrency.

## Architecture implemented

```text
Parent Codex
    ↓
persistent unsloth_local_agent MCP
    ↓
models.json allowlist and alias resolver
    ↓
cross-process Qwen single-flight lock
    ↓
child Codex with per-invocation model and context overrides
    ↓
Unsloth Studio supervisor and llama-server
```

### Automatic server startup

A forced `llama-server` termination initially left the running Studio supervisor with stale state: its API reported Q4 as loaded while no `llama-server` process existed. The original installed bridge failed in the same stale state, proving this was not caused by the wrapper.

After Unsloth Studio was restarted cleanly, its API correctly reported the model as unloaded. A Q4 delegation then caused the supervisor to start a new `llama-server`, load Q4, and complete the child task successfully.

### Concurrency

The wrapper uses a Windows file lock plus an in-process thread lock. The file lock is shared across separate MCP server processes, so Q4 and Q5 use one global Qwen worker slot.

The first concurrency implementation exposed a child-output capture problem after a queued request. Repeated `communicate(timeout=...)` calls could return no captured output, while poll-only handling could block when stderr filled its pipe.

The final implementation drains stdout and stderr continuously in reader threads while polling the child for timeout. In the passing test:

- the first request ran a deliberate sleep and completed with `FIRST`;
- the overlapping second request waited;
- the second started only after the first released the lock and completed with `SECOND`;
- no two Qwen children ran concurrently.

### Fresh-parent verification

The updated persistent registration was tested from:

1. a separate fresh normal `codex exec` parent; and
2. the restarted Codex desktop parent.

Both parents discovered the new tools. The restarted desktop parent successfully completed explicit Q5 and default Q4 delegations.

## MCP progress, cancellation, and locking fix

Date: 2026-08-30

### Problem reproduced

The implementation task initially recorded seven Qwen MCP calls as stalled.
Inspection showed that the local model was often still completing successful
provider turns while the parent saw neither a final result nor progress. The
wrapper used a synchronous MCP handler, buffered child output until process
exit, and waited indefinitely for its global Windows file lock. Cancelling the
parent call therefore did not reach the running `codex.exe` child, and later
Qwen calls could wait invisibly behind it.

The obsolete native `qwen38_worker` ChatGPT-account error was a separate route
and remains removed. This fix changes only the persistent MCP wrapper behavior.

### Implementation

`C:\Users\henry\.codex\unsloth_mcp\server.py` now:

- exposes `spawn_local_agent` as an asynchronous MCP tool;
- launches child Codex with `asyncio.create_subprocess_exec`;
- drains JSONL stdout and stderr continuously;
- reports safe activity counts through MCP progress notifications without
  exposing child output or reasoning;
- treats 900 seconds without child output as an inactivity timeout while
  retaining the existing 3500-second hard timeout;
- catches cancellation, terminates the complete Windows child process tree,
  awaits exit, and releases the lock;
- returns a busy error immediately when either the in-process or cross-process
  single-flight lock is occupied instead of creating an unobservable queue.

Model aliases, authentication, child configuration, the `medium` reasoning
default, and the global MCP registration were not changed.

## Reasoning-effort investigation and implementation

Date: 2026-08-30

### Conclusion

The MCP now defaults both Qwen3.8 aliases to `medium` through the dedicated child Codex configuration:

```toml
model_reasoning_effort = "medium"
```

`server.py` still passes only the selected model and context-window override, so this remains one shared MCP default rather than a per-call selector. Before this implementation, omitting an override allowed the Unsloth/Qwen template's `xhigh` default to apply.

The Qwen3.8 Studio control exposes exactly `None`, `Low`, `Medium`, `High`, and `Extra High`, plus a separate `Preserve thinking` toggle. Their request values are `none`, `low`, `medium`, `high`, and `xhigh`. `minimal` and `max` are not choices in this model's UI and are not remaining qualification cases.

This updates the earlier caution that effort levels should not be added before verification. First-party sources and live local tests confirm that the installed Q4 path accepts and applies Codex reasoning effort. The later implementation changed only the dedicated child `config.toml`; the MCP wrapper, model aliases, global registration, and authentication file were unchanged.

### Verified facts

- OpenAI's [Codex configuration reference](https://developers.openai.com/codex/config-reference) defines `model_reasoning_effort` for supported Responses API models. The [Codex v0.149.1 request builder](https://raw.githubusercontent.com/openai/codex/rust-v0.149.1/codex-rs/core/src/client.rs) maps the configured value to the nested Responses field `reasoning.effort`.
- Current upstream [Unsloth Responses handling](https://github.com/unslothai/unsloth/blob/main/studio/backend/routes/inference.py) reads `reasoning.effort` on `/v1/responses` and maps it to `reasoning_effort` plus `enable_thinking` before forwarding to the Chat Completions/llama.cpp path. Its adapter allowlist includes `none`, `minimal`, `low`, `medium`, `high`, `max`, and `xhigh`.
- The [llama.cpp server API](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) documents that `reasoning_effort = "none"` disables thinking and that other values are exposed to the Jinja template; its `/v1/responses` endpoint converts Responses requests to Chat Completions.
- The [Unsloth Qwen3.8 chat template](https://huggingface.co/unsloth/Qwen3.8-27B/raw/main/chat_template.jinja) defaults to `xhigh` when thinking is enabled, maps `high` to `xhigh`, and explicitly accepts `xhigh`, `medium`, or `low` in its thinking branch. `enable_thinking=false` emits the non-thinking prompt.
- The [Unsloth Qwen3.8-27B-GGUF model card](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF) says thinking is on by default, can be disabled per request, and depth can be tuned with `reasoning_effort`; it lists both `UD-Q4_K_XL` and `UD-Q5_K_XL` variants.
- The installed Studio backend identifies `preserve_thinking` as independent of current-turn thinking effort. When true, the Qwen template retains historical `<think>` blocks from prior assistant turns. The installed Qwen3.8 family default is true.
- The MCP wrapper, model aliases, and Q4 model catalog contain no effort field. The shared `medium` default lives only in the dedicated child `config.toml`. The local Q4 catalog advertises no supported reasoning levels and no reasoning summaries; those are Codex metadata values, not a runtime test of the Unsloth endpoint.

### Live local qualification

The running Studio endpoint was tested on the active `UD-Q4_K_XL` quant with the same short arithmetic task and a `512`-token output cap. Authentication stayed in memory and reasoning text was not printed or saved. This table covers every effort shown in the Qwen3.8 Studio control.

Test prompt: `Compute (137 * 89) + (46 * 237). Return only the integer.` The correct result is `23095`.

| Studio choice | Request effort | Status | Reasoning items | Reasoning characters | Output tokens | Visible answer |
| --- | --- | --- | ---: | ---: | ---: | --- |
| None | `none` | completed | 0 | 0 | 6 | `14585` (incorrect) |
| Low | `low` | completed | 1 | 206 | 149 | `23095` |
| Medium | `medium` | completed | 1 | 217 | 166 | `23095` |
| High | `high` | completed | 1 | 325 | 211 | `23095` |
| Extra High | `xhigh` | completed | 1 | 292 | 183 | `23095` |

This single sample is a protocol qualification, not a quality or latency benchmark. Generation is sampled, so character and token counts must not be read as a stable ranking. `none` conclusively disabled the reasoning channel in this request, but its one sampled answer was wrong. `high` and `xhigh` both worked; the Qwen3.8 template normalizes `high` to its `xhigh` branch, so their different token counts here are sampling variance rather than evidence of two different template tiers.

`Preserve thinking` was tested separately with Studio's local token-count endpoint and the same synthetic prior assistant reasoning block. No reasoning text was returned or saved.

| Preserve-thinking request | Input tokens | Interpretation |
| --- | ---: | --- |
| `false` | 37 | Historical reasoning removed |
| `true` | 642 | Historical reasoning retained |
| omitted | 642 | Qwen3.8 default matched `true` |

This verifies that `Preserve thinking` is a history-retention control, not a sixth effort level. It also verifies that the installed Qwen3.8 default currently preserves prior thinking when the field is omitted.

A separate real child Codex run used:

```text
model_reasoning_effort="low"
```

with the installed `unsloth_api` profile and Q4 model. It exited successfully and returned the required `EFFORT_OK`, confirming that Codex v0.149.1 accepts the explicit setting with this custom model even though the local catalog's supported-level list is empty.

It exited with code `0` and returned the required `MEDIUM_DEFAULT_OK`. Codex therefore loaded the child profile and completed a Qwen3.8 request with the configured default.

### Interpretation for this MCP

- Current MCP default: `medium`, set in the dedicated child Codex `config.toml` and shared by Q4 and Q5.
- The verified UI/request values are `none`, `low`, `medium`, `high`, and `xhigh`. `high` is normalized to `xhigh` by the Unsloth template.
- `none` is verified to disable thinking. Its incorrect answer in this one sample is a reason not to choose it as the coding-worker default without task-level evaluations.
- `Preserve thinking` is independent of effort. Its installed Qwen3.8 default is on; leaving it on retains earlier reasoning in multi-turn prompts and therefore uses more input context.
- `minimal` and `max` are not exposed for Qwen3.8 in Studio. Do not add them to this MCP's Qwen selector merely because the outer Responses adapter can parse those strings.
- The current MCP `spawn_local_agent` interface accepts a task and optional model only, so callers cannot choose effort per call. A per-call selector remains separate deferred work.

### Unknowns and limits

- Explicit effort was qualified against Q4. Q5 uses the same Qwen3.8 template family, but it was not separately exercised with an effort override.
- The local Q4 catalog still has empty supported levels and `supports_reasoning_summaries=false`. That stale metadata may keep effort controls out of some UI/model-selection surfaces even though an explicit Codex configuration works.
- The model card provides no separate quant-by-quant reasoning-effort benchmark. No Q4-versus-Q5 quality or latency claim is made.
